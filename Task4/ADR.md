### **Нефункциональные требования**

|**№**|**Требование**|

|2|Получение ставок не создаёт дополнительной нагрузки на АБС: кол-центр и выгрузка берут ставки из Kafka **[ASR]**|

### **Решение**

Диаграммы (PlantUML, нотация C4):
- [c4-context-rates-call-center.puml](c4-context-rates-call-center.puml) - диаграмма контекста.
- [c4-component-rates-call-center.puml](c4-component-rates-call-center.puml) - диаграмма компонентов (адаптер АБС и система кол-центра).

На диаграммах показано только то, что относится к передаче ставок. Интернет-банк, сайт и процесс заявок из задания 3 не меняются.

**Основные элементы**

Интеграционный адаптер АБС (Java Spring Boot):
- **Публикация ставок** - есть в MVP из задания 3. Публикует ставки в Kafka при каждом изменении в АБС.
- **Выгрузка ставок в файл** - новый компонент. Читает ставки из Kafka и формирует CSV-файл со всеми актуальными ставками.
- **Отправка файла** - новый компонент. Выкладывает файл на SFTP-сервер банка и повторяет попытку при ошибке.
- **Планировщик** - новый компонент. Раз в день запускает полную выгрузку, чтобы у партнёра всегда был свежий файл.

Система кол-центра (доработка через её штатные возможности расширения):
- **Приём ставок** - читает ставки из Kafka.
- **Справочник ставок** - таблица в PostgreSQL системы кол-центра.
- **API ставок и виджет ставок** - показывают оператору список депозитов и ставок в его рабочем месте.

SFTP-сервер банка - размещается в DMZ, у партнёра отдельная учётная запись с доступом только к своей папке.

**Логика решения**

1. **Источник ставок один - АБС.** Ставки уже ведутся там по процессу из MVP, поэтому кол-центры получают те же ставки, что сайт и интернет-банк
2. **Ставки берутся из Kafka, а не из АБС.** Топик ставок уже есть в MVP, а новые получатели не нагружают перегруженную базу АБС
3. **Система кол-центра читает Kafka сама.** Она написана на Java Spring Boot и поддерживает расширение. Доработку могут сделать подрядчик или Java-специалисты команды АБc
4. **Выгрузка для партнёра - в адаптере АБС.** Адаптер уже работает с Kafka и ставками, его сопровождает команда банка. Так не нужно поднимать отдельный сервис ради одного файла
5. **Партнёр получает файл, а не API.** Это ограничение партнёра. В файле всегда полный список ставок, поэтому партнёру не нужно собирать изменения из нескольких файлов
6. **SFTP-сервер на стороне банка.** Банк сам контролирует доступ и не зависит от инфраструктуры партнёра. Партнёр забирает файл, когда ему удобно.
7. **Ежедневная полная выгрузка.** Даже если отправка при изменении не прошла, на следующий день у партнёра будут правильные ставки

**Участвующие команды**

|Команда|Что делает|
| :- | :- |
|Команда АБС|Компоненты выгрузки ставок в адаптере АБС|
|Подрядчик системы кол-центра / Java-специалисты АБС|Приём ставок из Kafka, справочник и виджет ставок|
|IT-отдел (инфраструктура)|SFTP-сервер в DMZ, доступ для партнёра, мониторинг выгрузки|
|Партнёрский кол-центр|Загрузка файла в свою систему|
|Бизнес-представители банка|Скрипты звонков по депозитам для партнёрского кол-центра|

### **Альтернативы**

1. **Система кол-центра читает ставки напрямую из БД АБС.** Проще в разработке, но добавляет нагрузку на перегруженную базу АБС и связывает систему подрядчика со структурой таблиц АБС. Отклонено
2. **Ставки для кол-центра берутся из сервиса депозитов интернет-банка через REST.** Ставки там уже есть, но кол-центр начинает зависеть от доступности интернет-банка, а для партнёра всё равно нужен файл. Отклонено.
3. **Выгрузку для партнёра делает система кол-центра.** Ставки там уже есть, но это платформа подрядчика, а партнёрский кол-центр - другая компания. Связывать их через систему подрядчика неудобно. Отклонено
4. **Отдельный микросервис для выгрузки файлов.** Правильнее с точки зрения разделения ответственности, но для MVP это лишний сервис. Можно вынести, если файловых обменов станет больше
5. **Отправлять ставки партнёру по e-mail.** Просто, но ненадёжно, плохо автоматизируется на стороне партнёра и небезопасно. Отклонено

**Недостатки, ограничения, риски**

- **Ставки у партнёра обновляются с задержкой.** Файл забирается по расписанию партнёра, поэтому какое-то время оператор может видеть старые ставки. Нужно согласовать с партнёром частоту загрузки.
- **Нет подтверждения, что партнёр загрузил файл.** Банк видит только то, что файл выложен. Проверять загрузку придётся через партнёра.
- **Ставки в справочнике - только для консультации.** Финальную ставку по заявке всё равно подтверждает бэк-офис, иначе возможны споры с клиентом.
- **Зависимость от подрядчика системы кол-центра.** Доработку нужно согласовать с подрядчиком, чтобы она не сломалась при обновлении платформы.
- **Адаптер АБС получает ещё одну задачу.** Ошибка в выгрузке может затронуть приём заявок, поэтому компоненты выгрузки нужно изолировать внутри адаптера.
- **SFTP-сервер в DMZ - новая точка входа извне.** Нужны отдельная учётная запись, доступ только на чтение и контроль подключений.
- **Всё зависит от ставок в АБС.** Пока справочник ставок в АБС не сделан, передавать кол-центрам нечего - эта задача первая в дорожной карте.
